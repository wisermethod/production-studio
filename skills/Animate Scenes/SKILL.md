# Animate Scenes

## Context

Writes no script, narrates nothing, synthesizes no speech, captures nothing, cuts no recording, joins no scenes and sets no loudness. For an avatar scene or window, it sends the take's prepared narration upload and a render request to HeyGen through the API; for a full avatar scene only, the member may choose HeyGen's web app through Browser Control instead. It publishes nothing. It draws no explainer's picture: `skills/Animated Explainer/` and `skills/Illustrator/` in `wiser` make it. Use for the caller's made scenes: walkthroughs animate one product still through `tools/Scene Composer/` here and `tools/video-render/` in `wiser`; explainers run Animated Explainer by name; and, with a HeyGen account, avatar scenes show the member's selected avatar speaking the scene's current take. A walkthrough or explainer may instead carry an avatar window in the first clear corner under Avatar window for a stretch of its narration, added after the base renders and before review. A window is a presentation property, never another scene kind or take.

Upload retains narration at HeyGen. API Avatar V remains the ordinary route: uploads have no independent fee established; renders spend separate API-wallet dollars by rendered second, including padding or guards, at the selected look type's rate. The Cost step discloses that rate and the two-render amount before billing, as an estimate with no ceiling where the rate is unpublished. The attended web route spends the member's HeyGen web plan, by one approved submission, with its page readings and any unread amount disclosed separately. Never send `script` with a `voice_id`, use HeyGen's own speech or replace the take, even when the look is public.

When may the web route be offered? The member requests it, or a diagnosed API limitation prevents rendering and is neither a declined spend nor a denied action: offer it for a full avatar scene and wait for the member to choose it. An offer is not a selection; no answer leaves this work waiting, a decline stops it. A declined spend, denied action, missing connection's setup stop or unresolved API render: never offer or select web to clear that stop. It is never an automatic fallback. Reconcile any prior API submission's outcome and possible charge before proceeding; preserve it beside the web attempt. A reconciled failed API render and a web render are two attempts. Both routes require the member's `heygen` connection for the Look rule and status/download; web requires no wallet read, API render or API standing approval. A missing connection takes Gateway answers, never a web sign-in as a substitute.

Avatars are optional, offered once as available with a HeyGen account and never pressed. Without a connected `heygen` connector, make every scene that does not depend on it; a requested window can retain its rendered base while the window waits. A missing or unready connection takes Gateway answers below and **Connect Account** in its own human turn; never make the rest of a production wait for an account it does not need. An avatar stop or pending answer holds only its dependent work: record it and finish the other supplied scenes before returning that question or handoff.

Selecting an existing avatar asks no consent question and takes no sample. Under this plugin's Standing constraint, cloning a real person's voice clone or likeness asks once, before any sample, trusts the member's yes without proof and reuses a saved yes across productions. This skill clones neither. A request to make a new likeness from a photo, footage or webcam takes this plugin's declared gap, **Cloning a person's likeness**, before any sample is opened or sent; a saved yes does not close that gap. Member-supplied music and footage are treated as cleared.

All walkthrough labels are the script's checked `On-screen words`, chips are supplied text, and captions are the words narrated. This skill writes no prose. Captions in a written form different from the words narrated, an address or a symbol say, are missing here; report that gap rather than transcribing them into a different form. Animated Explainer binds its own memory keys. This skill's `design` is optional. Drawn captions over an avatar scene are also missing: stop that scene before upload when requested, name the gap and continue independent scenes.

Classifier seam: none.

## Objective

Make the supplied scenes in order, with one production frame, lead and tail, and write `<production>/scenes/scenes.json` for the assembling step. Keep a ready scene whose inputs have not changed without touching its files or running its tools. A new scene becomes ready only under an Animator ship verdict covering its key. Verify against Success.

`<production>/scenes/scenes.json` is a UTF-8 JSON object with these keys, which the assembling step reads by name:

- `frame`: `width`, `height` and `fps`, the production's target.
- `lead` and `tail`: the resolved production values, in seconds, shared by every scene so the assembling step can start each scene's narration at `lead`.
- `order`: the caller's scene ids in order.
- `scenes`: an object mapping each scene id to these keys:
  - `kind`: `walkthrough`, `explainer` or `avatar`.
  - `key`: step 2's full SHA-256, or `null` if a stop prevented its computation.
  - `folder`: the scene folder relative to the production, or `null` before one exists.
  - `inputs`: `record`, the `inputs.json` path relative to the production and its `sha256`; `script_sha256`; `take`, its `cid` and record `sha256`; `still_sha256` for a walkthrough or `sources` with each source's identity and `sha256` for an explainer; and `fonts`, each declaration's source path and `sha256`. Use `record: null` before filing and retain only hashes actually measured.
  - `outputs`: each existing output as an object with `path` relative to the production and `sha256`. Names are `timing_specification`, `timing`, `captions`, and, for a walkthrough, `specification`, `composition` and `render_record`; an explainer instead has `delivery_record`. A finished render adds `segment` and `frame_hashes`. `project` lists its files with the same path and hash shape. `review_record` names a saved verdict where present. For avatar work, also retain `avatar_job`, the saved generation inputs, ids and answers; `avatar_evidence`, a list of relative `path`/`sha256` objects for every upload, padded WAV, receipt, completion marker, original download and conform/evidence bundle file; and, for a window, `base_segment` and `composite_receipt`. An avatar's decoded frame hashes come from the conform receipt, and a window's from the composite receipt, retained as `frame_hashes`. A prior generation may be referenced only after its Generation inputs match and its file identities pass. Missing files have no entry; never substitute an earlier key's output.
  - `window`, only where requested: `from`, `to`, `look`, `corner` and `rect` (the chosen corner and its resolved rectangle in production pixels), `acceptance: {corner, target, interval, words, date}` for any overlap the member accepted, with `interval` its accepted scene-local frame range `[s, e)` with an exclusive end, `start_frame: s` (its first visible frame) and `end_frame: e` (the exclusive end, last visible frame `e - 1`), derived by the window pass. A `window` entry without `corner` or `rect` is valid: resolve placement on the next window pass and never refuse the record for those missing fields.
  - `window_drops`, when present: a list of `{from, to, look, words, date}`, each recording the window the member dropped at the exhausted-corner choice, with its exact boundaries and look, the member's exact words and date. Earlier entries without it have no recorded drop.
  - `duration` and `frames`: numbers from the timing output, on the scene's own entry beside `outputs`, or `null` before it returns.
  - `state`: `ready`, `unreviewed`, `unfinished` or `stopped`. `unreviewed` has `owed`, an array naming the Animator review or unresolved findings; `unfinished` has `owed` from the explainer's record; `stopped` has `reason`. Duplicate keys, invalid states, missing required fields or a ready scene with a mismatched review key stop the run with the malformed field named; leave that record unchanged. ## Pitfalls

- **Ambiguous request or missing cue entry.** Ask for the unknown before making that scene; never infer the scene set, a target, label or chip text.
- **A frame requested at its own decimal time.** That decimal can name the frame before it. Use step 6's midpoint and verify the returned frame number.
